# 电子速购 · E-SHOP Express

> 面向跨境电商的多语言内容处理与本地化推荐平台
> 中文商品文案 → 12 语种译文 → 平台合规预检 → 可发布草稿 → 本地化推荐 → 买家侧搜索

一个从「翻译工具」出发、最终长成完整链路的后端项目。**重点不在功能数量，而在于每个技术选择都能说清代价**——文末列了已知限制与设计取舍。

---

## 这个项目解决什么问题

跨境卖家的真实困境不是"翻译不出来"，而是三件更麻烦的事：

| 问题 | 现状 | 本项目的做法 |
| :--- | :--- | :--- |
| 术语前后不一致 | 同一批货里"纯棉"译成三种说法 | 术语库作为**翻译前约束**注入 prompt，翻译后只校验落地率、不改写译文 |
| 一个文案要发多个市场 | 每个语种重写一遍 | 一次生成三版：忠实原文 / 文化适配 / SEO 优化 |
| 不知道发出去会不会被拒 | 平台合规靠人工盯 | 按平台禁用词预检 + 字符上限校验 |

**换句话说**：这是一个把「翻译 → 合规 → 发布 → 推荐 → 搜索」串成闭环的系统，而不是一个翻译接口的包装。

## 技术栈

| 层 | 选型 |
| :--- | :--- |
| 语言 / 运行时 | Java 17、Spring Boot 3 |
| 网关 | Spring Cloud Gateway（JWT 验签 + 身份头注入） |
| 数据访问 | JdbcTemplate（**刻意不用 ORM**，见「设计取舍」） |
| 存储 | MySQL 8（16 表，雪花 ID）、Redis（缓存 + 熔断） |
| 搜索 | MySQL ngram 全文索引 + Elasticsearch（IK 分词）双路，可降级 |
| 数据同步 | Canal 订阅 binlog → ES 增量同步 |
| AI 能力 | DeepSeek（OpenAI 兼容协议）、SBERT 向量检索（独立 Python 服务） |
| 前端 | Vue 3 + Vite 5（中 / 英 / 阿三档界面，支持 RTL） |

```

                        └────────┬────────┘
                                 │
        ┌────────────┬───────────┼───────────┬────────────┐
        ▼            ▼           ▼           ▼            ▼
   auth:8081   catalog:8082  translation:8083  recommendation:8084  platform:8085
   登录注册     商品/搜索     翻译（LLM）       推荐               术语/发布/客服/管理
        │            │           │           │            │
        └────────────┴───────────┴───────────┴────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                  ▼
          MySQL 8            Redis            Elasticsearch
         (雪花 ID)         (缓存+熔断)      (可选，IK 分词)
                                 │
                    ┌────────────┴────────────┐
                    ▼                         ▼
              Canal (binlog)          embedding :10683
              MySQL → ES 增量同步      SBERT 向量推理（Python）
```

**六个服务按业务边界切分，不是按技术分层切分**——`catalog` 只管商品与检索、`translation` 只管翻译，跨服务走 HTTP。好处是每个服务可独立重启（部署时只重启过 `translation-service` 验证改动）。

## 技术亮点（含量化数据）

> 数据口径：**实测**＝跑出来的；**代码统计**＝静态扫描。缺线上流量的指标不写入。

### 1. 鉴权：把角色装进 token，网关统一拦截

登录时把 `role_keys` / `permissions` 签进 JWT，网关验签后向下游注入 `X-User-Id`，**下游服务零查库**。

- 覆盖 53 个对外接口，9 个管理路径需 `admin` 角色（`GatewayAccessRules`，有单测）
- 伪造签名、过期、空 token 全部 401
- **代价**：权限变更是签发时快照，24h 内不生效

### 2. 缓存：给 Redis 加超时与熔断

Redis 不可达时不拖垮接口，而是快速失败。

| 指标 | 数值 |
| :--- | :--- |
| 超时 / 熔断阈值 | 2s / 连续 3 次失败冷却 30s |
| 命中时延迟 | 0.17s |
| Redis 故障时（降级） | 2.3s（加熔断前 **96s**） |

缓存失效放在事务提交之后，避免并发回填旧值。

### 3. 搜索：双路召回 + 静默降级

| 路径 | 实现 | 适用 |
| :--- | :--- | :--- |
| 主 | Elasticsearch + IK 分词 | ES 可用时 |
| 备 | MySQL 全文索引（ngram 解析器） | ES 宕机自动回落，前端零改动 |

- 修复中文短词召回：重建 16 列联合 ngram 索引，「连衣裙」**5 → 38** 条
- 切 ES + IK 归一化后，「T恤」**28 → 171** 条
- **已知缺口**：MySQL 全文索引只覆盖 8 语种，缺 `th/vi/ms/id/tl`，ES 关闭时东南亚五语种搜不到

### 4. 数据同步：Canal 订阅 binlog

- 增删改 **0.21s** 生效
- 用 `_update` + `doc` + `doc_as_upsert` 而非 `index` 覆盖，**保留关联字段**（`image_url` 不会被清空）
- 失败回滚位点 + 按业务主键幂等重放
- **代价**：Canal 停机期间的变更它看不到，需周期性 `reconcile` 补偿

### 5. 数据库：消除 N+1

商品列表从「每条查一次图片」改为**关联表批量预取 + 内存分组**：

| 指标 | 优化前 | 优化后 |
| :--- | ---: | ---: |
| 单页 20 条商品的 SQL 次数 | 41 | **5**（-88%） |
| 随页大小增长 | 线性 | 常数 |

### 6. 翻译：术语作为约束，不是事后替换

**踩过坑才改对**的设计：

> 最初是"译完后把中文术语替换成译文"。但在**中→外**方向上，译文里根本不含中文术语，替换没有可定位的目标；强行替换还会破坏目标语言形态（阿拉伯语、俄语尤明显）。

改成：

```
翻译前 → 术语召回（同义词归一化 → 字面匹配 → 长词优先）
       → 按「强制 / 参考」两级拼成 constraint_block 注入 prompt
翻译后 → 只校验术语落地（checked / violations / compliance_rate）
       → 只上报，不改写译文
```

- 一次产出三版：`versionA` 忠实原文 / `versionB` 文化适配 / `versionC` SEO 优化
- 术语召回区分**强制**（原文命中，强约束）与**参考**（语义相关，仅供参考）
- 文化说明固定简体中文（面向国内运营，不随目标语种变化）

### 7. 推荐：混合召回 + LLM 精排

内容召回（SBERT 语义 + 关键词命中 + 国家匹配系数）→ 协同补位 → LLM 做「主品 / 配件 / 无关」三分类 → 按文化标签重排。

- 配件类误配占比 **29.6% → 12.5%**，单次精排 1.82s
- **诚实说明**：没做用户协同过滤。推荐接口不接收 `user_id`，"协同"是同国家 + 同品类偏好的**人群分层**，不是用户向量相似度

### 8. RAG 智能客服

28 条 FAQ + 2382 件商品双路索引；FAQ 强命中（≥0.65）时丢弃商品召回；生成受检索资料约束并回传引用来源。

- hit@1 = 12/12（**12 条小样本，按 FAQ 反推的口语化改写，不是线上准确率**）
- 无关问题全部拒答
- 模型不可用时降级返回检索原文，而非报错

## 快速开始

### 前置依赖

| 依赖 | 必需性 | 缺失后果 |
| :--- | :--- | :--- |
| JDK 17 | 必需 | 全部服务起不来 |
| MySQL 8 | 必需 | 起不来（**不能用 MariaDB**，不支持 `utf8mb4_0900_ai_ci`） |
| DeepSeek API Key | 必需 | 翻译与客服不可用 |
| Redis | 可选 | 有熔断降级，但推荐会变慢 |
| Elasticsearch | 可选 | 关闭后搜索走 MySQL 全文索引 |
| Canal | 可选 | 不启则 ES 不增量同步 |
| Python + SBERT | 可选 | 推荐降级、RAG 客服不可用 |

### 配置

```bash
# 1. Python 侧
cp .env.example .env        # 填入 LLM_API_KEY、JWT_SECRET_KEY

# 2. Java 侧（Spring Boot 不读 .env，必须用 env.bat）
cd backend-java
cp env.example.bat env.bat  # 填入 DB_PASSWORD、JWT_SECRET_KEY、LLM_API_KEY
```

> `JWT_SECRET_KEY` 必须两边一致，否则 auth 签发的 token 网关验不过 → 全站 401。

### 启动

```bat
cd backend-java
run-all.bat
```

按依赖顺序启动 8 个进程（embedding → auth → catalog → translation → recommendation → platform → gateway → 前端），已占端口的自动跳过，日志在 `backend-java/logs/`。单服务调试用各自的 `start-<name>.bat`。

### 前端

```bash
cd frontend
npm install
npm run dev      # http://localhost:20682
npm run build    # 产物到 dist/
```

### 云服务器部署

见 [`deploy/cloud/README.md`](deploy/cloud/README.md)：环境变量模板、一键启停脚本、Nginx 配置、防火墙最小化开放。

## 设计取舍：几个"故意不这么做"

这部分比功能列表更能说明工程判断。

| 决定 | 理由 |
| :--- | :--- |
| **不用 ORM，用 JdbcTemplate** | 业务里有 13 语种宽表查询、ES/MySQL 双路切换、大批量预取。ORM 的实体映射在这些场景下是负担而非便利 |
| **不引入 Kafka** | 场景是**数据同步**（binlog → ES），不是消息队列。Canal 直接订阅 binlog 更轻，Kafka 需额外维护 broker 且要写生产者 |
| **翻译不做字符级 diff** | 阿语/泰语前端分词不可靠，字符 diff 会给误导结果。改为整段决策（采纳 A / 采纳 B） |
| **权限不查库，装进 token** | 换取「零查库」，代价是权限变更 24h 内不生效。中小企业后台可接受，但必须知道边界 |
| **RAG 不用向量库** | 数据量只有 28 + 2382 条，内存暴力检索足够。引入 Milvus/Qdrant 是过度设计 |
| **发布只生成草稿** | **不调任何平台开放 API**，不会真的上架。合规校验也**只按平台禁用词**，不是按国家法规 |

## 已知限制

诚实列出，因为每条都是明确的下一步：

1. **MySQL 全文索引缺 5 个语种**（`th/vi/ms/id/tl`），ES 关闭时这些语种搜不到
2. **翻译缓存缺失**：`translation-service` 无 Redis 代码，相同文案重复翻译会重复计费。若补缓存，**键必须含 `user_id`**，否则 A 用户的术语约束结果会被 B 用户命中
3. **登出只清前端 token**：JWT 无状态，服务端不做失效，旧 token 在 24h 内仍有效。改进方向：黑名单 / 短 TTL + refresh token / 密码版本号
4. **`versionC`（SEO 版）未落库**：表里只有 `version_a` / `version_b`，SEO 版用完即丢
5. **埋点表字段不足**：`biz_rec_stat_log` 只有 4 列，无 `user_id` / `keyword` / `lang`，导致「搜索→详情转化率」「零结果率」无法计算
6. **买家界面语言只有 3 档**（中/英/阿），虽然商品字段存了 13 个语种；且标题语言由**卖家发布时选的语种**决定，与买家无关
