# MySQL → Elasticsearch 同步操作手册

> 一句话：**开三个服务（MySQL / ES / Canal）+ 跑一个同步进程**，之后的增删改就实时同步了。

---

## 一、全貌

```
①  MySQL      3306   数据源（binlog 必须是 ROW 格式）
②  Elasticsearch  9200   同步目标（索引 product）
③  Canal      11111  binlog 中间件（实例 product_sync）
        ↕
④ 同步进程（Python）  ← 从 Canal 拉 binlog → 转文档 → 写 ES
```

四个角色，缺任何一个同步都不工作。**①②③ 是常驻服务，④ 是需要主动启动的进程。**

---

## 二、日常启动（每次开机后，3 步）

### 第 1 步：确认 MySQL 与 ES

```bat
REM ES 若没启动：双击（或命令行运行）
<ES_HOME>\bin\elasticsearch.bat

REM MySQL 一般已随系统/服务启动，确认 3306 在监听即可
netstat -ano | findstr :3306
```

### 第 2 步：启动 Canal

```bat
<项目根>\deploy\canal\start_canal.bat
```

双击后会开一个新窗口常驻，看到下面这行就说明实例起来了：

```
--> init table filter : ^ecommerce\.(product|product_image)$
... start successful....
```

### 第 3 步：启动同步进程

```bat
<项目根>\deploy\canal\start_all.bat
```

`start_all.bat` 会**自动检查三个依赖服务**，全部就绪才启动同步；缺哪个会明确告诉你该启动什么。

如果三个服务都已就绪，也可以直接跑 `start_sync.bat`（不检查依赖）。

### 三个启动脚本的区别

| 脚本                | 作用                                              | 何时用             |
| :---------------- | :---------------------------------------------- | :-------------- |
| `start_canal.bat` | 启动 **Canal Server**（JDK 8，实例 product_sync）      | 开机后若 Canal 没在跑  |
| `start_all.bat`   | **检查 3306 / 9200 / 11111 → 打印 status → 启动同步进程** | **推荐**，日常启动同步用它 |
| `start_sync.bat`  | 只启动同步进程，不检查依赖                                   | 已确认依赖都在跑，想少等几秒  |

> `start_all.bat` 与 `start_sync.bat` 的**最终动作完全相同**（都是 `canal_sync run`），  
> 区别只在 `start_all.bat` 前面多了一段依赖检查 + 状态打印，能避免"窗口开了但其实没生效"。  
> 而 `start_canal.bat` 是**另一个层级**——它启动的是 Canal 服务端，不是同步进程。

### ⚠️ bat 文件必须保持纯 ASCII（踩过的坑）

这三个脚本**不能出现中文**，否则会"双击后一闪而过、什么都没发生"。

**原因**：中文 Windows 的 cmd 在 `chcp 65001` 生效**之前**，是按本地代码页（GBK）去解析 `.bat` 文件的。  
UTF-8 编码的中文字节被按 GBK 解读时会**逐字节错位**，可能把注释内容当成命令执行：

```
'璧栫己澶辨椂缁欏嚭鎻愮ず骞堕
```

脚本会在中途报 `<乱码> 不是内部或外部命令` 然后终止，看起来就像"无法正常启动"。

**约定**：

- 改这些脚本时，注释和提示**一律用英文**
- 或把文件另存为 ANSI / GBK 编码
- 自查方法：`python -c "print(open(r'deploy\canal\start_all.bat','rb').read().isascii())"` → 应为 `True`

> 当前三个脚本已全部改为英文（纯 ASCII），并已实测通过。

## 三、首次部署（只做一次）

前面第二节假设 ES 索引已经建好。**如果是全新的库/索引**，需要额外两步：

```bat
REM 1. 建索引 + 全量导入（含 JOIN product_image 取主图）
cd /d <项目根>
.venv\Scripts\python.exe -m backend.search.es_sync recreate

REM 2. 然后按第二节启动 Canal 与同步进程
```

> **为什么必须先全量再增量**：Canal 从启动时的最新位点开始监听，  
> 看不到历史变更。历史数据必须由全量同步补齐。

### MySQL 侧的一次性准备

```sql
-- canal 账号（需要复制权限）
CREATE USER IF NOT EXISTS 'canal'@'%'
  IDENTIFIED WITH mysql_native_password BY 'canal123456';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';
FLUSH PRIVILEGES;

-- binlog 必须是 ROW 格式（可在 my.ini 配置，改完重启 MySQL）
--   log-bin=mysql-bin
--   binlog-format=ROW
--   server-id=1
```

## 四、验证同步是否在正常工作

### 方式 1：看状态（最快）

```bat
cd /d <项目根>
.venv\Scripts\python.exe -m backend.canal.canal_sync status
```

期望输出：

```json
{
  "canal": { "connected": true, "destination": "product_sync" },
  "es": { "available": true, "index": "product", "doc_count": 2382 },
  "mysql_product_count": 2382,
  "in_sync": true          ← 关键：数量一致
}
```

### 方式 2：改一条数据看是否同步

随便改一条商品的标题，等 1~2 秒，然后在 Kibana / curl 里查 ES：

```bash
curl -sk -u "elastic:$ES_PASSWORD" \
  "https://localhost:9200/product/_doc/<esin>"
```

### 方式 3：只监听不写 ES（排查用）

```bat
.venv\Scripts\python.exe -m backend.canal.canal_sync listen
```

会实时打印 binlog 事件，用来确认「变更有没有推过来」。

## 五、停止

| 要停的东西 | 怎么停                              |
| :---- | :------------------------------- |
| 同步进程  | 在它的窗口按 `Ctrl+C`                  |
| Canal | 关闭 `start_canal.bat` 的窗口         |
| ES    | 关闭 ES 窗口 / `taskkill /PID <pid>` |

只停同步进程、保留 Canal 是安全的：Canal 会把变更缓冲住，下次启动同步进程会接着消费。

## 六、常见问题

| 现象                                 | 原因                                    | 处理                                                                  |                            |
| :--------------------------------- | :------------------------------------ | :------------------------------------------------------------------ | -------------------------- |
| ES 里的数据和 MySQL 不一致                 | 同步进程没跑                                | 跑 `start_all.bat`                                                   |                            |
| 改了数据但 ES 没变                        | Canal 没启动 / 位点已越过                     | 检查 11111 端口；必要时跑一次 `es_sync full` 补差                                |                            |
| `status` 里 canal.connected = false | Canal 未启动                             | 跑 `start_canal.bat`                                                 |                            |
| 改商品图片后 ES 没更新                      | filter 没包含 product_image，或改完没重启 Canal | 确认 \`filter.regex=ecommerce\\.(product                              | product_image)\` 并重启 Canal |
| 启动 Canal 报 JAVA_HOME 无效            | JDK 路径变了                              | 改 `start_canal.bat` 里的 `JAVA_HOME`（当前指向 `.jdks\corretto-1.8.0_422`） |                            |
| 长时间没同步，启动后只有新数据                    | Canal 从最新位点开始                         | 跑 `es_sync full` 补齐历史，再启动同步进程                                       |                            |

## 七、建议的运维习惯

| 频率 | 动作                  | 目的                        |
| :- | :------------------ | :------------------------ |
| 每天 | `es_sync reconcile` | 清理 MySQL 已删但 ES 残留的孤立文档   |
| 每周 | `es_sync full`      | 兜底刷新（如换图这类非 binlog 覆盖的场景） |
| 按需 | `canal_sync status` | 确认 `in_sync: true`        |

> Canal 会漏掉「它没运行期间」的变更（比如电脑关机时改的数据），  
> 所以定期对账 + 全量兜底是必要的，别只依赖增量。

## 八、命令速查

```bash
# ---- 同步 ----
python -m backend.canal.canal_sync run        # 常驻增量同步（最常用）
python -m backend.canal.canal_sync once       # 拉一轮就退出（验证用）
python -m backend.canal.canal_sync status     # 状态检查
python -m backend.canal.canal_sync listen     # 只打印事件，不写 ES

# ---- 全量 / 对账 ----
python -m backend.search.es_sync recreate     # 重建索引 + 全量导入
python -m backend.search.es_sync full         # 全量导入（不删索引）
python -m backend.search.es_sync reconcile    # 删除对账
python -m backend.search.es_sync status       # 环境检查

# ---- 脚本 ----
deploy\canal\start_canal.bat   # 启动 Canal
deploy\canal\start_all.bat     # 检查依赖 + 启动同步（推荐）
deploy\canal\start_sync.bat    # 直接启动同步（不检查依赖）
```
